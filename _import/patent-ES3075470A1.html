Abstract

The invention includes a method and system for encrypting data. The method comprises providing a distributed network comprising network holders (h) and resource-constrained devices (d) that generate private data (m); encrypting the private data (m) to generate encrypted data (c); and sending the encrypted data (c) to an intermediary server where it is sliced into a set of slices (c i). The method further comprises determining a subset of network holders (h j) to whom to send the set of slices (c i); generating, for each pair of resource-constrained device (d) and network holder, a decryption key (rk) based on any combination of the public/private key pairs of the resource-constrained device (d) and the network holder, wherein the decryption keys (rk) are accessible only by the intermediary server; and decrypting each slice (c i) with the respective decryption key (rk). [0007] TECHNICAL SECTOR
[0008] The present invention relates generally to distributed confidential computing and particularly to methods and systems for encrypting data that can be decrypted and processed on a distributed network while preserving confidentiality.
[0011] BACKGROUND OF THE INVENTION
[0012] Outsourcing computing to the cloud is crucial for resource-constrained devices such as Internet of Things (IoT) devices. This type of computing allows a resource-constrained client to expand its computing capacity by outsourcing computing to other nodes or clouds. However, outsourcing computing can raise some privacy concerns, especially when devices share sensitive data with each other. Resource-constrained devices encrypt the data they generate before sending it to the cloud. While encryption methods exist that can prevent the cloud provider from accessing the encrypted data and protect it against data breaches, transmitting that encrypted data through traditional mechanisms involves complex key management. Furthermore, the data needs to be decrypted before it can be used.
[0013] Some privacy-preserving technologies have proven highly beneficial in outsourced computing implementations, as they allow operations to be performed on sensitive data. Two key technologies among these are Fully Homomorphic Encryption (FHE) and Multi-Party Secure Computing (MPC).
[0014] FHE allows computation to be performed on encrypted data without revealing the plaintext data, making it suitable for outsourcing operations to a single server. However, FHE has some drawbacks when working with encrypted data provided by multiple clients, and this is typically resolved with distributed protocols for decryption keys using Shared Secret techniques.
[0015] On the other hand, MPC is a family of cryptographic protocols that allow a group of participants to jointly compute a function on their private input data without revealing anything other than the result. While traditional MPC is designed for direct, interactive computation between the owners of the input data, some studies propose MPC in a service provider context (see, for example, M. Burkhart, et al., “SEPIA: Privacy-Preserving Aggregation of Multi-Domain Network Events and Statistics,” 2010). This approach delegates the computation entirely to a set of computing nodes while guaranteeing data privacy. Some research has suggested using MPC as a solution for resource-constrained devices.
[0016] MPC protocols are primarily based on Shared Secrets, which offer considerable flexibility, guaranteeing privacy as long as enough participants among the computing nodes remain uncorrupted. Specifically, a secret value 'x' is divided into 'n' distinct pieces {x!} for 'i=1 to n', where each piece is assigned to a different fork. With a corruption threshold of t<n, only a valid set of 't+1' pieces can reconstruct the original secret 'x', and operations can be performed directly on these pieces. However, this approach has some limitations: while increasing the number of forks of the secret pieces improves security, it also places a load on the device when sharing sensitive information. In particular, if there are ‘n’ compute nodes (piece forks), the device must establish ‘n’ separate confidential channels (ci...c<n>) to transmit the private value ‘x’, sending a piece {x!} of ‘x’ through each channel (see Figure 1), resulting in ‘n’ encrypted data. For a large value of ‘n’, this can be impractical for resource-constrained devices that need to send private data periodically. Furthermore, to share ‘x’ with a group of forks, each fork must be known to the device before it can send each piece, and the device must have access to the plaintext of ‘x’ to compute the pieces. If a value previously shared with one group of forks is to be shared with a different group, either the previous group performs a re-sharing protocol to the new group, or the device must retrieve the plaintext of ‘x’ and perform a new sharing phase with the new group of forks.
[0017] Therefore, there is a state-of-the-art need for a method and system for encrypting data that can overcome the problems mentioned above and allow a resource-constrained device to dynamically choose a distributed network of forks and share a secret with that network without the need to transmit 'n' independent values through n separate confidential channels, and that guarantees the complete confidentiality of the transmission of the secret from the resource-constrained devices to the network holders of the distributed network.
[0018] DESCRIPTION OF THE INVENTION
[0019] A first object of the present invention is a computer-implemented method for sharing encrypted data, characterized in that said method comprises the steps of:
[0020] provide a distributed network comprising a plurality of network holders (h), where each network holder (h) possesses a holder public key (pk<h>) and a holder private key (sk<h>);
[0021] provide at least one resource-constrained device (d) that generates private data (m), wherein each resource-constrained device (d) possesses a device public key (pk<d>) and a device private key (sk<d>);
[0022] encrypt, by at least one of the resource-constrained devices (d), the private data (m) using its device public key (pk<d>) and an additive homomorphic encryption algorithm, generating an encrypted data (c);
[0023] send, by at least one of the resource-limited devices (d), the encrypted data (c) to an intermediary server;
[0024] determine a subset of network holders (h¡) within the plurality of network holders (h) to which the pieces (c¡) of the encrypted data (c) are sent by the intermediary server;
[0025] fragment, by the intermediary server, the encrypted data (c) into the set of pieces (c¡) such that the plaintext data of the encrypted data (c¡) make up a set of plaintext data pieces (m¡) of the private data (m);
[0026] generate, for each pair of resource-constrained device (d) and network holder from the subset of network holders (h<j>), a re-encryption key (rk) based on any combination of the public/private key pair (pk<d>, sk<d>) of the particular resource-constrained device (d) with the public/private key pair (pk<h>, sk<h>) of the particular network holder, such that the re-encryption keys (rk) are only accessible by the intermediary server; and
[0027] The intermediary server re-encrypts each piece (c¡) with the respective decryption key (rk) corresponding to the pair comprising the resource-constrained device (d) that generates the encrypted data (c) and the network owner (h¡) with whom the piece (c¡) must be shared, generating a set of re-encrypted pieces (c¡’). In other words, since a decryption key (rk) has been generated for each particular piece (c¡) that must be sent from the source resource-constrained device (d), which has generated the private data (m) (encrypted as the corresponding encrypted data (c)) to the destination network owner (h<j>), for whom said particular piece (c¡) must be sent, said decryption key (rk) is used to re-encrypt that particular piece (c¡).
[0028] The decryption keys (rk) can be generated by the data owner when the private keys of the EANs required for generation are available. Otherwise, a three-party protocol must be executed involving the resource-constrained device (d), the corresponding network owner (h), and the intermediary server, where only the intermediary server learns the decryption keys. In any case, the intermediary server does not know the private keys (sk<d>, sk<h>) of the resource-constrained devices or the network owners. The network owners do not have access to or knowledge of the decryption keys at any stage of the data encryption process; otherwise, they could compromise the private key of the resource-constrained device.
[0029] As used herein, a distributed network may refer to a network in which each network holder can communicate with any other holder without accessing a centralized point.
[0030] As used herein, a resource-constrained device may refer to having, by design, limited storage and processing capabilities, such that it performs its tasks with minimal energy consumption while remaining cost-effective.
[0031] As used herein, a public key is a key that is available to anyone who wants to send an encrypted message to the owner of the private key. It can be used to encrypt data and can be freely shared. The private key, on the other hand, can be kept secret and can be used to decrypt the encrypted message.
[0032] The holder's public key (pk<h>) and private key (sk<h>) are typically generated on the relevant holder network (h), and the methods for generating these keys (pk<h>, sk<h>) should be compatible with the additive homomorphic encryption algorithm used to generate the encrypted data (c). NTRU is an example of such a key generation method, although others may exist.
[0033] The device's public key (pk<d>) and private key (sk<d>) can be generated by the corresponding resource-constrained devices (d) or can be generated externally by a user and sent to the respective resource-constrained device (d). The methods for generating these keys (pk<d>, sk<d>) must be compatible with the additive homomorphic encryption algorithm used to generate the encrypted data (c). NTRU is one such key generation method, although others may exist.
[0034] Therefore, the method described in this document allows resource-constrained devices to encrypt the information they generate using their own public keys. Then, either immediately afterward or at a later, not necessarily consecutive, point in time, an intermediary server, acting as a communication link between the resource-constrained devices and the network owners, re-encrypts and sends the newly encrypted data to the network owners. After decrypting the data with their private keys, the network owners can recover their portion of the data in plaintext. In this way, absolute confidentiality of the information is guaranteed throughout the entire process, since only the intermediary server knows the encryption keys (neither the resource-constrained devices nor the network owners know them), and only the network owners know their private keys, which are used to decrypt the encrypted information.
[0035] In some cases, the method also involves the intermediary server sending each re-encrypted piece (c¡’) to the corresponding network holder of the subset of network holders (h<j>). These re-encrypted pieces (c¡’) can be decrypted with the corresponding private keys (sk<h>) of the network holders of the subset of network holders (h<j>). In this way, a new set of encrypted data (c¡ = Enc(pk<d>; m¡)) can be obtained from the encrypted data (c), such that the set of pieces of the plaintext data (m¡) can be used to reconstruct the original plaintext data (m) using a shared secret scheme, and each piece (c¡) of the encrypted data has been re-encrypted into a new encrypted data (c¡’) that can be decrypted with the holder's private key (sk<h>). Therefore, only the holder (h¡) who has received the encrypted data fragment (c¡’) has the ability to decrypt the fragment (c¡), which contains the fragment ‘m¡’ of the original plaintext data (m). This minimizes the risk of a single device having the ability to decrypt all the fragments and therefore access the original value ‘m’.
[0036] In some cases, the decryption key (rk) generation phase involves generating the decryption key (rk) based on the combination of the device private key (sk<d>) of at least one of the resource-constrained devices (d) with the network owner's public key (pk<h>) or private key (sk<h>). Using the private key (sk<d>) of the resource-constrained device (d) to generate the decryption keys (rk) means that only the device—that is, the owner of the private data—can authorize decryption to a group of owners, and that neither the intermediary server nor any other participant can steal the encrypted data without prior authorization from the device.
[0037] In some cases, the decryption key (rk) is generated based on the combination of the device private key (sk<d>) and the network owner's private key (sk<h>) through an interactive protocol between the resource-constrained device (d), the corresponding network owner (h), and the intermediary server. Only the intermediary server learns the value of the decryption key (rk), and the device private key (sk<d>) and the network owner's private key (sk<h>) remain confidential, accessible only to the resource-constrained device (d) and the network owner (h), respectively. In other words, neither the resource-constrained device (d) nor the network owner (h) has access to or can learn the decryption key (rk), and none of the entities (device, owner, and intermediary server) involved in the interactive protocol will know each other's private keys.
[0038] In some cases, the encryption key (rk) is generated by at least one of the resource-constrained devices (d) or by running a protocol shared between the resource-constrained device (d), the corresponding network holder (h), and the intermediary server.
[0039] In some cases, resource-constrained devices (d) are Internet of Things (IoT) devices. As used herein, IoT devices can refer to non-standard computing hardware, such as sensors, actuators, or household appliances, that connect wirelessly to a network and can transmit data. Examples of IoT devices include smart meters.
[0040] In some cases, resource-constrained devices (d) generate private data (m) continuously or periodically.
[0041] In some cases, the encryption phase of the private data (m) that generates an encrypted data (c) is carried out at a time 'tT'; and the phases in which the subset of network holders (h<j>) from the plurality of network holders (h) is determined, the encrypted data (c) is sliced into a set of slices (c¡), the decryption keys (rk) are generated, and each slice (c¡) is decrypted with the corresponding decryption key (rk) are carried out at a time 't2', where time 't2' occurs after time 'tT'. In other words, the generation of the encrypted data may be carried out at a particular time, but the decryption of that encrypted data (including the phases of choosing the network holders, slicing, generating the decryption keys, and decrypting the slices) to be sent to the corresponding network holders may be carried out later. These two phases of the process—generating the encrypted data and decrypting the fragments—do not need to be executed sequentially. In fact, the encrypted data could be stored in memory and accessed later for processing and decryption. This is possible thanks to the additive homomorphism property of the encryption scheme, which allows the fragments of the encrypted data to be generated blindly, and thanks to the decryption algorithm, which allows the new recipient of each encrypted fragment to be determined. Other solutions in the literature involve either having access to the plaintext data to generate the new fragments or using encrypted data that can be processed independently by each user, incurring a significant computational load.

[0054] The solution disclosed in this document offers several advantages over existing solutions. It presents a lightweight and dynamic solution that allows resource-constrained devices to share data, such as shared secrets, by sending a single encrypted data point, thus avoiding the need for multiple independent confidential channels. It is lightweight because it achieves a constant amortized communication cost for sharing private data on the device side, which, in addition to the encryption key generation process, is independent of the number of owners. Therefore, it is particularly efficient when sharing data from the device to a network of owners on a regular basis. It is dynamic because private data can be encrypted with the device's public key (pk<d>), shared elsewhere, and the group of owners (h) to receive the fragmented version of the secret (m) can be selected at a later time. Furthermore, this method not only allows for more efficient sharing of private data (m) via shared secret, but also enables interoperability with other standard techniques such as the recovery of encrypted data (c) and its decryption by the device, or simply the re-encryption of the encrypted data to the public key of a different trusted recipient who can obtain the complete plaintext data from the new encrypted data. All the specified methods can be selected after the original encrypted data (c) has been generated.
