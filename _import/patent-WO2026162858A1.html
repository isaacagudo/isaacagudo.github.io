Abstract

The present invention relates to methods and systems for sharing encrypted data. The method comprises providing a distributed network comprising network owners (h) and resource-constrained devices (d) that generate private data (m); encrypting the private data (m) to generate encrypted data (c); and sending the encrypted data (c) to a proxy server where they are split into a set of pieces (ci). The method further comprises determining a subset of network owners (hj) to which the set of pieces (ci) is sent; generating, for each resource-constrained device (d) and network owner pair, a re-encryption key (rk) based on any combination of the public/private key pairs of the resource-constrained device (d) and the network owner, wherein the re-encryption keys (rk) can only be accessed by the proxy server; and re-encrypting each piece (ci) with the respective re-encryption key (rk).

ANTECEDENTES DE LA INVENCIÓN BACKGROUND OF THE INVENTION

Externalizar la computación a la nube es crucial para los dispositivos limitados en recursos como los dispositivos del Internet de las cosas (loT). Este tipo de computación permite a un cliente limitado en recursos expandir su capacidad de cómputo mediante la externalización de la computación a otros nodos o nubes. Sin embargo, la externalización de la computación puede generar algunos problemas de privacidad, especialmente cuando los dispositivos comparten datos sensibles entre ellos. Los dispositivos limitados en recursos cifran los datos que generan antes de enviarlos a la nube. A pesar de que existen métodos de cifrado que pueden prevenir el acceso a los datos cifrados por parte del proveedor de la nube y también los protegen ante violaciones de datos, transmitir esos datos cifrados a través de mecanismos tradicionales implica una gestión de claves compleja. Además, los datos necesitan ser descifrados antes de que puedan ser utilizados. Outsourcing computing to the cloud is crucial for resource-constrained devices such as Internet of Things (IoT) devices. This type of computing allows a resource-constrained client to expand its computing capacity by outsourcing computing to other nodes or clouds. However, outsourcing computing can raise some privacy concerns, especially when devices share sensitive data with each other. Resource-constrained devices encrypt the data they generate before sending it to the cloud. While encryption methods exist that can prevent the cloud provider from accessing the encrypted data and protect it against data breaches, transmitting that encrypted data through traditional mechanisms involves complex key management. Furthermore, the data needs to be decrypted before it can be used.

Algunas tecnologías para la preservación de la privacidad han demostrado ser muy beneficiosas ante implementaciones de externalización de la computación, ya que permiten que las operaciones sean ejecutadas sobre datos confidenciales. Entre esas tecnologías podemos encontrar dos principales: el Cifrado Completamente Homomórfico (FHE) y la Computación Segura Multiparte (MPC). Some privacy-preserving technologies have proven highly beneficial in outsourced computing implementations, as they allow operations to be performed on sensitive data. Two key technologies among these are Fully Homomorphic Encryption (FHE) and Multi-Party Secure Computing (MPC).

FHE permite realizar la computación sobre datos cifrados sin revelar los datos en claro y, por ello, es adecuado para externalizar las operaciones en un solo servidor. Sin embargo, FHE presenta algunos inconvenientes a la hora de trabajar con datos cifrados provistos por múltiples clientes, y esto se resuelve normalmente con protocolos distribuidos para las claves de descifrado utilizando técnicas de Secreto Compartido. FHE allows computation to be performed on encrypted data without revealing the plaintext data, making it suitable for outsourcing operations to a single server. However, FHE has some drawbacks when working with encrypted data provided by multiple clients, and this is typically resolved with distributed protocols for decryption keys using Shared Secret techniques.

Por otro lado, MPC es una familia de protocolos criptográficos que permiten a un grupo de participantes calcular conjuntamente una función sobre sus datos de entrada privados sin revelar nada más que el resultado. Mientras que el MPC tradicional está diseñado para la computación directa e interactiva entre los propietarios de los datos de entrada, algunos estudios proponen MPC en un contexto de proveedor de servicios (ver,por ejemplo, M. Burkhart, etal, “SEPIA: Privacy-Preserving Aggregation of Multi-Domain Network Events and Statistics,” 2010). Este enfoque delega la computación completamente a un conjunto de nodos de computación mientras que garantiza la privacidad de los datos. Algunas investigaciones han sugerido usar MPC como solución para dispositivos limitados en recursos. On the other hand, MPC is a family of cryptographic protocols that allow a group of participants to jointly compute a function on their private input data without revealing anything other than the result. While traditional MPC is designed for direct, interactive computation between the owners of the input data, some studies propose MPC in a service provider context (see, for example, M. Burkhart et al., “SEPIA: Privacy-Preserving Aggregation of Multi-Domain Network Events and Statistics,” 2010). This approach delegates the computation entirely to a set of computing nodes while ensuring data privacy. Some research has suggested using MPC as a solution for resource-constrained devices.

Los protocolos MPC se basan principalmente en Secretos Compartidos, los cuales ofrecen mucha flexibilidad, garantizando la privacidad siempre que suficientes participantes entre los nodos de computación permanezcan sin corromper. Específicamente, un valor secreto ‘x’ se divide en ‘n’ trozos distintos {x¡} para ‘¡=1 a n’, donde cada trozo se asigna a un tenedor diferente. Con un umbral de corrupción de t<n, solamente un grupo válido de ‘t+1 ’ trozos puede reconstruir el secreto original ‘x’, y las operaciones pueden ser realizadas directamente sobre estos trozos. Sin embargo, este enfoque tiene algunas limitaciones: mientras que el incremento del número de tenedores de trozos del secreto mejora la segundad, también impone una carga en el dispositivo a la hora de compartir información sensible. En particular, si hay ‘n’ nodos de computación (tenedores de trozos), el dispositivo debe establecer ‘n’ canales confidenciales separados (ci...cn) para transmitir el valor privado ‘x’, enviando un trozo {x¡} de ‘x’ a través de cada canal (ver Figura 1), resultando en ‘n’ datos cifrados. Para un valor de ‘n’ grande, esto puede ser impráctico para dispositivos con recursos limitados que necesitan enviar datos privados de forma periódica. Además, para compartir ‘x’ con un grupo de tenedores, cada uno de ellos debe ser conocido por el dispositivo antes de poder enviar cada trozo y el dispositivo debe tener acceso a la forma claro de ‘x’ para poder calcular los trozos. Si se desea que un valor previamente compartido con un grupo de tenedores sea compartido con un grupo diferente, o bien el grupo anterior realiza un protocolo de recompartición hacia el nuevo grupo, o bien el dispositivo debe recuperar el texto plano de ‘x’ y realizar una nueva fase de compartición con el nuevo grupo de tenedores. MPC protocols are primarily based on Shared Secrets, which offer considerable flexibility, ensuring privacy as long as enough participants among the computing nodes remain uncorrupted. Specifically, a secret value 'x' is divided into 'n' distinct pieces {x!} for 'x! = 1 to n', where each piece is assigned to a different fork. With a corruption threshold of t < n, only a valid set of 't + 1' pieces can reconstruct the original secret 'x', and operations can be performed directly on these pieces. However, this approach has some limitations: while increasing the number of forks of the secret pieces improves security, it also places a load on the device when sharing sensitive information. In particular, if there are 'n' compute nodes (piece forks), the device must establish 'n' separate confidential channels (c_i... c_n ) to transmit the private value 'x', sending a piece {x_i} of 'x' through each channel (see Figure 1), resulting in 'n' encrypted data. For a large value of 'n', this can be impractical for resource-constrained devices that need to send private data periodically. Furthermore, to share 'x' with a group of forks, each fork must be known to the device before it can send each piece, and the device must have access to the plaintext of 'x' to compute the pieces. If a value previously shared with one group of forks is to be shared with a different group, either the previous group performs a re-sharing protocol to the new group, or the device must retrieve the plaintext of 'x' and perform a new sharing phase with the new group of forks.

Por tanto, existe una necesidad en el estado del arte de un método y sistema para cifrar datos que sean capaces de superar los problemas citados previamente y que permitan a un dispositivo limitado en recursos elegir de forma dinámica una red distribuida de tenedores y compartir un secreto con dicha red sin la necesidad de transmitir ‘n’ valores independientes a través de n canales confidenciales separados y que garanticen la completa confidencialidad de la transmisión del secreto desde los dispositivos limitados en recursos hacia los titulares de red de la red distribuida. Therefore, there is a state-of-the-art need for a method and system for encrypting data that can overcome the problems mentioned above and allow a resource-constrained device to dynamically choose a distributed network of forks and share a secret with that network without the need to transmit 'n' independent values through n separate confidential channels, and that guarantees the complete confidentiality of the transmission of the secret from the resource-constrained devices to the network holders of the distributed network.

Otherwise, a three-party protocol must be executed involving the resource-constrained device (d), the corresponding network owner (h), and the intermediary server, where only the intermediary server learns the encryption keys. In either case, the intermediary server does not know the private keys (skd, skh) of the resource-constrained devices or the network owners. The network owners do not have access to or knowledge of the encryption keys at any stage of the data encryption process; otherwise, they could compromise the private key of the resource-constrained device.

Tal como se utiliza en el presente documento, una red distribuida puede referirse a una red en la que cada titular de red puede comunicarse con algún otro titular sin acceder a un punto centralizado. As used herein, a distributed network may refer to a network in which each network holder can communicate with any other holder without accessing a centralized point.

Tal como se utiliza en el presente documento, un dispositivo limitado en recursos puede referirse a tener, por diseño, almacenamiento y capacidades de procesamiento limitados, tal que ejecuten sus tareas con un consumo mínimo de energía sin dejar de ser rentables. As used herein, a resource-constrained device may refer to having, by design, limited storage and processing capabilities, such that it performs its tasks with minimal energy consumption while remaining cost-effective.

Tal como se utiliza en el presente documento, una clave pública es aquella clave que puede estar disponible para cualquiera que quiera enviar un mensaje cifrado al propietario de la clave privada. Puede ser usada para cifrar los datos y puede ser compartida libremente. La clave privada, por el contrario, puede mantenerse en secreto y puede utilizarse para descifrar el mensaje cifrado. As used herein, a public key is a key that is available to anyone who wants to send an encrypted message to the owner of the private key. It can be used to encrypt data and can be freely shared. The private key, on the other hand, can be kept secret and can be used to decrypt the encrypted message.

La clave pública del titular (pkh) y la clave privada del titular (skh) son generadas normalmente en la red de titulares correspondiente (h) y los métodos para generar dichas claves (pkh, skh) deberían ser compatibles con el uso del algoritmo de cifrado homomórfico aditivo que se utiliza para generar el dato cifrado (c). Un ejemplo de dichos métodos para generar las claves puede ser NTRU, aunque puede haber otros. The holder's public key (pkh) and private key (skh) are typically generated on the relevant holder network (h), and the methods for generating these keys (pkh, skh) should be compatible with the additive homomorphic encryption algorithm used to generate the encrypted data (c). NTRU is one such key generation method, although others may exist.

La clave pública del dispositivo (pkd) y la clave privada del dispositivo (skd) pueden ser generadas por los dispositivos limitados en recursos (d) correspondientes o pueden ser generadas externamente por un usuario y enviadas al dispositivo limitado en recursos (d) respectivo. Esos métodos para generar dichas claves (pkd, skd) deben ser compatibles con el uso del algoritmo de cifrado homomórfico aditivo que se utiliza para generar el dato cifrado (c). Un ejemplo de dichos métodos para generar las claves puede ser NTRU, aunque puede haber otros. The device's public key (pkd) and private key (skd) can be generated by the corresponding resource-constrained devices (d) or externally by a user and sent to the respective resource-constrained device (d). The methods for generating these keys (pkd, skd) must be compatible with the additive homomorphic encryption algorithm used to generate the encrypted data (c). NTRU is one such key generation method, although others may exist.

Por tanto, el método descrito en el presente documento permite que los dispositivos limitados en recursos cifren la información que ellos mismos generan mediante sus propias claves públicas y que, o bien inmediatamente después o en un instante futuro no necesariamente consecutivo, un servidor intermediario dispuesto en términos de comunicación entre los dispositivos limitados en recursos y los titulares dered recifre y envíe los nuevos datos cifrados a los titulares de red tal que, después de descifrar con la clave privada de los titulares, puedan recuperar su parte del dato en claro. De esta forma la confidencialidad absoluta de la información está garantizada durante todo el proceso ya que solo el servidor intermediario conoce las claves de recifrado (ni los dispositivos limitados en recursos ni los titulares de red las conocen) y solo los titulares de red conocen sus claves privadas las cuales serán usadas para descifrar la información recifrada. Therefore, the method described herein allows resource-constrained devices to encrypt the information they generate using their own public keys. Then, either immediately afterward or at a later, not necessarily consecutive, point in time, an intermediary server, acting as a communication link between the resource-constrained devices and the network owners, re-encrypts and sends the newly encrypted data to the network owners. After decrypting the data with their private keys, the network owners can recover their portion of the data in plaintext. In this way, absolute confidentiality of the information is guaranteed throughout the entire process, since only the intermediary server knows the encryption keys (neither the resource-constrained devices nor the network owners know them), and only the network owners know their private keys, which are used to decrypt the encrypted information.

En el paso 21 del método 20, se provee una red distribuida que comprende una pluralidad de titulares de red (h). Estas claves públicas de titular (pkh) y claves privadas de titular (skh) pueden haber sido generadas por los respectivos titulares de red (h). In step 21 of method 20, a distributed network comprising a plurality of network holders (h) is provided. Each network holder (h) in the distributed network has their own public holder key (pkh) and private holder key (skh). These public holder keys (pkh) and private holder keys (skh) may have been generated by the respective network holders (h).

En el paso 22 del método 20 se provee al menos un dispositivo limitado en recursos (d) que genera datos privados (m), donde cada dispositivo limitado en recursos (d) tiene una clave pública de dispositivo (pkd) y una clave privada de dispositivo (skd). In step 22 of method 20, at least one resource-limited device (d) is provided that generates private data (m), where each resource-limited device (d) has a device public key (pkd) and a device private key (skd).

En el paso 23 del método 20, cada dispositivo limitado en recursos (d) cifra su propio dato privado (m) utilizando su clave pública de dispositivo (pkd) y un algoritmo de cifrado homomórfico aditivo, generando un dato cifrado (c). In step 23 of method 20, each resource-constrained device (d) encrypts its own private data (m) using its device public key (pkd) and an additive homomorphic encryption algorithm, generating an encrypted data (c).

En el paso 24 del método 20, cada dispositivo limitado en recursos (d) envía los datos cifrados (c) que ha generado al servidor intermediario. Estos datos cifrados (c) podrían ser enviados al servidor intermediario a través de un solo canal. In step 24 of method 20, each resource-constrained device (d) sends the encrypted data (c) it has generated to the intermediary server. This encrypted data (c) could be sent to the intermediary server through a single channel.

En el paso 25 del método 20 se determina un subconjunto de titulares de red (h¡) de la pluralidad de los titulares de red (h), con los que se comparte el conjunto de trozos (c¡) del dato cifrado (c). In step 25 of method 20, a subset of network holders (h¡) is determined from the plurality of network holders (h), with whom the set of pieces (c¡) of the encrypted data (c) is shared.

En el paso 26 del método 20, el servidor intermediario trocea cada dato cifrado (c) en un conjunto de trozos (c¡) donde los datos en claro contenidos en los datos cifrados (c¡) conforman un conjunto de trozos de datos en claro (m¡) del dato privado (m) donde cada trozo de dato en claro (m¡) está contenido en el trozo correspondiente (c¡). In step 26 of method 20, the intermediary server slices each encrypted data (c) into a set of pieces (c¡) where the plaintext data contained in the encrypted data (c¡) make up a set of plaintext data pieces (m¡) from the private data (m) where each plaintext data piece (m¡) is contained in the corresponding piece (c¡).

En el paso 27 del método 20, se genera una clave de recifrado (rk) para cada par de dispositivo limitado en recursos (d) y titular de red del subconjunto de titulares de red (hj). Las claves de recifrado (rk) están basadas en cualquier combinación del par de claves público/privada (pkd, skd) del dispositivo limitado en recursos particular (d) con el par de claves público/privada (pkh, skh) del titular de red particular. En otras palabras, la clave de recifrado que se utilizará para recifrar un trozo (c¡), trozo el cual es parte del dato cifrado (c) generado por el dispositivo limitado en recursos ‘A’ y que debe ser enviado al titular de red ‘B’, será generado en base a cualquier combinación del par de claves público/privada (pkA, skA) del dispositivo limitado en recursos ‘A con el par de claves público/privada (pks, sks) del titular de red ‘B’. Por ejemplo, dicha clave de recifrado (rkAB) puede ser generada mediante la combinación de la clave privada (skA) del dispositivo limitado en recursos ‘A con la clave pública (pks) o la clave privada (skB) del titular de red ‘B’.Estas claves de recifrado (rk) pueden ser generadas por el propietario de los datos cuando las claves privadas de los titulares de red no son requeridas para la generación o también se puede ejecutar un protocolo compartido entre el correspondiente dispositivo limitado en recursos (d) y el correspondiente titular de red (h) implicado en la transmisión del trozo recifrado particular (c¡’) y el servidor intermediario. En cualquier caso, el servidor intermediario no conoce las claves privadas (skd, skh) de los dispositivos limitados en recursos y los titulares de red. Los titulares de red no tienen acceso o conocen las claves de recifrado (rk) en ninguna fase del proceso para cifrar los datos, en caso contrario podrían comprometer la clave privada del dispositivo (skd). In step 27 of method 20, a decryption key (rk) is generated for each resource-constrained device (d) and network holder (hj) pair within the subset of network holders. The decryption keys (rk) are based on any combination of the public/private key pair (pkd, skd) of the particular resource-constrained device (d) with the public/private key pair (pkh, skh) of the particular network holder. In other words, the decryption key used to decrypt a chunk (c), which is part of the encrypted data (c) generated by resource-constrained device 'A' and to be sent to network holder 'B', will be generated based on any combination of the public/private key pair (pkA, skA) of resource-constrained device 'A' with the public/private key pair (pks, sks) of network holder 'B'. For example, such a decryption key (rkAB) can be generated by combining the private key (skA) of resource-constrained device 'A' with the public key (pks) or the private key (skB) of network owner 'B'. These decryption keys (rk) can be generated by the data owner when the network owners' private keys are not required for generation, or a shared protocol can be executed between the relevant resource-constrained device (d) and the relevant network owner (h) involved in the transmission of the particular decrypted chunk (c¡') and the intermediary server. In either case, the intermediary server does not know the private keys (skd, skh) of the resource-constrained devices and the network owners. The network owners do not have access to or knowledge of the decryption keys (rk) at any stage of the data encryption process; otherwise, they could compromise the device's private key (skd).

En el paso 28 del método 20, el servidor intermediario recifra cada trozo (c¡) con la respectiva clave de recifrado (rk) que se corresponde con el par que comprende el dispositivo limitado en recursos (d) que genera el dato cifrado (c) y el titular de red (hj), a quien debe ser enviado el trozo (c¡) en particular, generando el conjunto de trozos recifrados (c¡’). Por todo esto, ya que una clave de recifrado (rk) ha sido generada para cada trozo (c¡) en particular que debe ser enviado desde el dispositivo limitado en recursos (d) como emisor, el cual ha generado el dato privado (m) (cifrado como el correspondiente dato cifrado (c)), al titular de red (hj) como destinatario, hacia el que se debe enviar dicho trozo (c¡) en particular, y donde que la clave de recifrado (rk) se utiliza para recifrar dicho trozo (c¡) en particular. Por el ejemplo mencionado previamente donde la clave de recifrado (rkAB) es generada para transmitir el trozo (c¡) entre el dispositivo limitado en recursos ‘A’ y el titular de red ‘B’, el servidor intermediario recifra el trozo (c¡) con la clave de recifrado (rkAB) generando el correspondiente trozo recifrado (c¡’). In step 28 of method 20, the intermediary server re-encrypts each piece (c¡) with the respective re-encryption key (rk) that corresponds to the pair comprising the resource-constrained device (d) that generates the encrypted data (c) and the network owner (hj), to whom the particular piece (c¡) must be sent, generating the set of re-encrypted pieces (c¡’). Therefore, since a re-encryption key (rk) has been generated for each particular piece (c¡) that must be sent from the resource-constrained device (d) as the sender, which has generated the private data (m) (encrypted as the corresponding encrypted data (c)), to the network owner (hj) as the recipient, to whom said particular piece (c¡) must be sent, and where the re-encryption key (rk) is used to re-encrypt said particular piece (c¡). For the previously mentioned example where the re-encryption key (rkAB) is generated to transmit the chunk (c¡) between the resource-limited device ‘A’ and the network holder ‘B’, the intermediary server re-encrypts the chunk (c¡) with the re-encryption key (rkAB) generating the corresponding re-encrypted chunk (c¡’).
